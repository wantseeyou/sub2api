状态：实现与代码审查完成；验证结果见文末。未调用真实上游核销或外部邮箱。

## 已确认的业务规则

### 邮件配置与通知

- 共用一套 SMTP 配置，配置、测试与发信不依赖邮箱认证或站内用户订阅到期提醒。
- 上游账号限额通知独立启用，保留现有金额限额提醒。
- 本次新增 OpenAI OAuth 账号达到自动停调阈值时的邮件通知。
- 站内用户邮箱认证、订阅到期提醒与管理员账号限额通知是不同用途。

### 网关服务设置

三个新开关默认关闭；仅适用于正常启用的 OpenAI OAuth 账号，不要求逐个开启旧的账号级自动用卡。

| 功能 | 已确认触发条件 | 已确认动作 |
| --- | --- | --- |
| 自动恢复状态 | 默认每 1 分钟检查；账号因额度阈值临时不可调度，确认上游 7 日已用额度归零 | 解除此次额度停调，不以 5 小时用量阻止此次恢复；同一次归零只恢复一次，之后允许原有规则再次暂停 |
| 临期自动用卡 | 已达到停调阈值，且有距离到期不超过 X 天的卡；X 默认 1 天，可修改 | 使用最早到期的有效卡；未达到停调阈值时不使用 |
| 停调后自动用卡 | 已达到停调阈值并进入相应临时不可调度状态，且有可用卡 | 使用最早到期的有效卡，不要求该卡已临期 |

停调阈值沿用“平台账号自动停调阈值”与单账号覆盖规则，不新增一套已用百分比标准。人工关闭调度与非额度原因的错误不属于自动恢复目标。

### 账号测试连接

- 文本测试提示词默认 `hi`，管理员可手动填写，空白时回退为 `hi`。
- 请求使用实际填写的内容，覆盖 OpenAI 普通与 Compact、Claude、Grok、Gemini 及兼容协议路径。
- 文本与媒体提示词独立保存，避免切换图片、视频等模式时互相覆盖；后台自动探测保留原有默认内容。

## 已核实的现状与原因

### 邮件

- 后端 SMTP 发信没有邮箱认证前置条件；问题在前端把 SMTP 配置与测试入口隐藏在 `email_verify_enabled` 后面。
- 订阅到期提醒和管理员账号限额通知已经有各自独立开关，通知卡片本身并未嵌套在邮箱认证开关内。
- 原管理员限额通知发送给已配置且启用的管理员收件地址，触发范围是支持本地金额配额的账号；OpenAI OAuth 原生 5 小时／7 日额度不在其中。

证据：`frontend/src/views/admin/SettingsView.vue:8474`、`:8637`、`:8704`、`:8795`；`backend/internal/service/email_service.go:145`；`balance_notify_service.go:183`；`gateway_usage_billing.go:540`。

### 状态未恢复

- 通用停调阈值对 OpenAI 的 5 小时／7 日任一窗口生效。平台默认值可被账号覆盖；多个窗口同时命中时取最晚恢复时间。
- 停调会持久化临时不可调度状态，原因中有 `source=account_scheduling_threshold`；正常刷新额度没有提前清除此记录，上游提前重置后仍受旧恢复时间阻断。
- 界面的“7 日已用为 0”也可能只是本地根据缓存重置时间推算，不能作为实际归零的唯一依据。
- 已有清理接口范围较宽，可能同时清除其他临时故障、模型限流等；本次自动恢复不能直接把它们视为只清额度原因的接口。
- 若 7 日归零但 5 小时仍达到阈值，恢复后下一次原规则评估可能再次暂停；用户已经接受这一行为，只要求同一次归零恢复一次。

证据：`backend/internal/service/account_scheduling_threshold_eval.go:33`、`:410`；`ratelimit_service.go:165`、`:2258`；`account_scheduling_threshold_reason.go:59`；`account_usage_service.go:1537`；`backend/internal/repository/account_repo.go:2585`。

### 已有用卡能力

- 账号管理 → 编辑普通 OpenAI OAuth 账号 → 5h／7d 自动暂停阈值下方，已有“自动使用重置卡”；默认关闭，独立用卡阈值默认均为 100%。这不是本次要沿用的通用停调阈值。
- 上游查询和前端已支持逐卡到期时间，列表可展开查看其他卡；尚无“临期 X 天”自动用卡策略。
- 自动用卡服务每分钟扫描，但仓储的 active 筛选会排除未来的限流与临时不可调度账号，无法直接覆盖本次需要检查的暂停账号。
- 已有固定 worker、扫描锁与数据库幂等记录。自动核销支持指定卡及兑换请求 ID，超时重试保持原卡和原请求 ID，无法确认原卡时不改用下一张。
- 已有防重保护有额度周期等边界；不能把本地模拟测试等同于真实上游在所有情况下的幂等保证。

证据：`frontend/src/components/account/EditAccountModal.vue:2668`；`frontend/src/components/account/OpenAIQuotaResetCell.vue:133`；`backend/internal/service/openai_quota_auto_reset.go:230`、`:298`、`:535`、`:607`；`openai_quota_service.go:338`、`:351`；`backend/internal/repository/account_repo.go:1040`。

## 实现方案

### 邮件事件

- 新 OpenAI 通知复用现有管理员账号限额通知开关、SMTP 和收件地址。
- 在账号确实进入阈值停调后发送，内容包含账号、触发窗口、已用百分比、阈值与预计恢复时间。
- 同一次停调按账号、停调事件和收件人去重，成功结果可重放；恢复后再次停调属于新事件。SMTP 超时或发送后记录失败时，无法保证绝对只投递一次。
- 邮件失败应记录并按现有通知机制处理，不阻断请求调度或额度自动化。邮件不因随后自动用卡而变成站内订阅提醒。

### 状态、用卡与并发

- 复用现有后台服务，使用明确包含额度暂停账号的分页候选查询，按已有固定并发处理；自动恢复不依赖前端页面保持打开。
- 先直接查询上游新额度。缺失 7 日窗口、查询失败或缓存推算的 0 都不能触发归零恢复。
- 自动恢复开启且识别出尚未处理的归零事件时，先恢复，此轮不消费卡。
- 持久化归零处理标记，重启和多实例不能重复处理同一事件；后续可信非零观测或新的额度周期用于识别下一次归零。
- 恢复时条件化清除与本次观察相符的额度停调记录，并同步缓存，避免覆盖并发出现的其他故障或人工操作。
- 两个全局用卡开关形成一套候选条件：仅临期开启时要求卡临期；停调后用卡开启时允许任意有效卡。命中两项也只进入一次核销流程。
- 核销前复核最新账号状态、暂停原因、实际额度及卡有效性；失败保持合理的停调状态。请求结果不明时先处理原兑换，不盲目换卡补偿。
- 用卡成功后刷新真实额度并恢复对应额度限制；不能借机清除非额度故障，也不能重新开启人工关闭的调度开关。

### 新旧策略兼容

保留现有账号级配置。两个全局用卡开关均关闭时保留旧账号级行为；任一个开启后统一按新策略处理，防止旧阈值提前消费或重复触发。全局策略直接覆盖全部正常启用的 OpenAI OAuth 账号，无须管理员逐个配置。仅开启自动恢复状态不接管旧用卡策略。

## 影响与验证

- 影响范围：管理设置 UI 与接口、设置持久化、OpenAI 后台额度处理、额度停调恢复、管理员通知、调度缓存，以及账号测试弹窗与测试请求构造。Claude Code 不参与新增额度自动化。
- 数据与并发：无需数据库迁移；配置存于 `openai_quota_automation`，归零标记存于账号 `extra.codex_7d_zero_recovery`。按主键分页读取候选 ID，复用 4 个额度 worker；邮件使用 2 个固定 worker 和有界队列。恢复通过单行条件更新与同事务 outbox 同步调度状态，缓存仅删除匹配的旧状态，兼容既有回填格式。
- 回退：关闭三个新开关即可停止新增恢复和用卡策略；两个全局用卡开关都关闭时沿用账号级配置。旧策略仍跳过已持久化的临时故障和限流。
- 上游边界：已确认接口和本地解析能力；未调用真实上游验证低于 100% 时能否消费指定卡或上游幂等语义。被上游拒绝时不得报告成功、伪造额度或无界重试。
- 验收：邮箱认证及订阅提醒关闭时仍可配置与测试 SMTP、发送管理员限额通知；OpenAI 阈值停调发邮件且同次停调不重复；三个开关默认关闭；暂停账号无页面访问也能被检查；真实 7 日归零仅恢复一次；5 小时仍超阈值时允许后续再次暂停；临期但未停调不消费；两开关同时命中不重复核销；其他平台与人工停用不被误操作。
- 复用既有前后端测试和构建。按需临时验证查询失败、缺字段、缓存推算归零、并发停调变化、重启、多实例、核销结果不明与通知失败；完成后清理临时产物，不新增长期保留测试。
